## 1. Context

`metacrunch new [--test] [--force] PATH` creates one kind of file: a filter
job that reads JSON Lines from stdin and writes them to stdout, and with
`--test` a Minitest test for it. The job's name is the file name, so a name
with parts (`catalog:ids`) cannot be created at all.

Since then, metacrunch has gained projects (`Metacrunchfile`), commands and
transforms. A new user who wants a project copies the layout from the
Readme or from `examples/project`; transforms, commands and the sources and
sinks of their own (a class each, until the extension gems are ported)
start from an empty file. The specs of sub-projects 7 and 8 left
`new --command` and `new --transform` for later.

This sub-project splits the command in two, as Rails, Hanami, Angular and
Nest do:

- `metacrunch new DIR` creates a **project**: a `Metacrunchfile`, a
  `Gemfile`, a `Rakefile`, the directories for jobs, transforms, commands
  and helpers, and a test that checks that the project loads.
- `metacrunch generate KIND NAME|PATH` creates a **job, transform, command,
  source or sink**, each with a test. A name places the file by convention
  in the project; a path places it anywhere, also without a project.

Every generated file runs right away, and every generated test passes.

Rejected alternatives:

- **One `new KIND NAME` for everything** (like `dotnet new`): a project and
  a file inside a project are different operations. One needs no project,
  the other needs one to place the file; one command would mix both rules.
- **Flags on today's `new`** (`new --transform PATH`): keeps the path as the
  only address, so names with parts still have no place.
- **`generate` only inside a project** (strict Rails): drops the single
  executable job or command file without a project, which the Readme
  recommends for personal tools.
- **Templates as heredocs in Ruby** (as today): with about 25 templates the
  code grows long and interpolation mixes with the generator's logic.
- **Thor** for templates, `--force` and conflict prompts: the first runtime
  dependency besides `logger`, only for generators.

### 1.1 Goals

- `new DIR` creates a project that loads, lists nothing in `--help`, and
  whose `rake test` passes.
- `generate KIND NAME|PATH` for `job`, `transform`, `command`, `source` and
  `sink`, with a test by default for names.
- A name maps to a file in the project; `:` becomes a directory.
- After generating, metacrunch checks that the project loads the new name.
- `Metacrunch.load_command`, and `Testing.invoke` with a command object, so
  that a command file given by path can be tested.
- `examples/project` follows the layout that `generate` creates.

### 1.2 Non-goals

- `destroy`, an alias `g`, templates overridden by the project, a gem
  generator (`new --gem`), `--pretend`, interactive conflict resolution.
- `git init`, `bundle install`, credentials, `.gitignore` in `new`.
- RSpec templates.
- Editing the `Metacrunchfile` when its globs miss a new file.

### 1.3 Success criteria

- `metacrunch new catalog`, then in `catalog/` `metacrunch generate` of all
  five kinds by name: `metacrunch --help` lists the job, transform and
  command, each runs with `exe/metacrunch`, the generated tests pass, and
  RuboCop with the repository's configuration finds no offense in the
  generated project.
- The same for all five kinds by path, without a project and with `--test`.
- Every error and note of sections 3 to 5 has a test.
- Line and branch coverage stay above the thresholds of `test/test_helper.rb`
  (95 % / 90 %).

### 1.4 Decisions

Approved by the user on 2026-10-18:

- `new` for projects and `generate` for the other artifacts, as in Rails.
- Kinds: `job`, `transform`, `command`, `source`, `sink`. No gem generator.
- A name needs a project and places the file by convention; a path works
  anywhere (rule 1 of the questions). A name without a project is a usage
  error.
- `:` in a name becomes a directory (`catalog:ids` → `jobs/catalog/ids.rb`);
  after writing, metacrunch loads the project again and notes when the new
  name is missing.
- Tests are generated by default for names, not for paths; `--[no-]test`
  overrides it. Minitest only.
- `new` creates an empty skeleton without sample jobs; a test of the
  project keeps it green.
- Templates are ERB files; generators are small classes that return the
  files to write.
- No alias `g`: generating is rare, and `g` would reserve a one-letter name.
- `generate` takes `--desc TEXT` for the `desc:` of jobs, transforms and
  commands.
- A command given by path gets a test through `Metacrunch.load_command` and
  `Testing.invoke` with a command object (option a), rather than refusing
  `--test`.
- `examples/project` is moved to the layout of `generate`.
- The Readme's Gemfile line gets `branch: "metacrunch-ng"`, since `master`
  holds 4.x until 5.0 is released.

Amended from planning (2026-10-18): `-` becomes `_` in file names (3.1);
sources and sinks never reopen a class of Ruby or metacrunch (3.1, 4.1);
`new` without DIR and the `.rb` message (5.2), the `cd` line (5.3); the
`use` line of a transform by path (6.2); `Generators::Files` and
`Generators::Skeleton` (8); Prism instead of `ruby -wc`, and what the
end-to-end test generates in-process and checks with RuboCop (10).

## 2. Command line

```
metacrunch new [--force] DIR
metacrunch generate KIND [--[no-]test] [--desc TEXT] [--force] NAME|PATH
```

Both commands accept their options before and after the arguments
(`OptionParser#permute!`, as `credentials` does). `generate` becomes a
reserved name (`Names::RESERVED`); `new` already is.

`metacrunch --help` lists them as:

```
  new          Create a project
  generate     Create a job, transform, command, source or sink
```

`metacrunch generate --help` (and `help generate`):

```
Usage: metacrunch generate KIND [OPTIONS] NAME|PATH

Create a job, transform, command, source or sink.

Kinds:
  job        jobs/NAME.rb: reads JSON Lines from stdin and writes them to stdout
  transform  transforms/NAME.rb: steps that jobs use
  command    commands/NAME.rb: a body that invokes jobs and commands
  source     lib/NAME.rb: a class that yields records
  sink       lib/NAME.rb: a class that writes records

A NAME (catalog:ids) places the file in the project of the working directory,
with a test in test/. A PATH (tools/fix.rb) places it there, without a test
unless --test is given.

Options:
        --[no-]test        Create a test (default: for a NAME)
        --desc TEXT        Description for metacrunch --help (job, transform, command)
        --force            Overwrite existing files
    -h, --help             Show this help
```

## 3. Targets of `generate`

The argument is a **path** if it contains `/` or `.` (`Names.path?`, the
rule of `run`, `check` and `trace`), else a **name**.

### 3.1 Names

A name needs a project: the nearest `Metacrunchfile` at or above the working
directory. The file goes below the project root, and `:` separates
directories:

| Kind | Name | File | Test |
|---|---|---|---|
| `job` | `catalog:ids` | `jobs/catalog/ids.rb` | `test/jobs/catalog/ids_test.rb` |
| `transform` | `catalog:clean` | `transforms/catalog/clean.rb` | `test/transforms/catalog/clean_test.rb` |
| `command` | `catalog:release` | `commands/catalog/release.rb` | `test/commands/catalog/release_test.rb` |
| `source` | `marc:dump` | `lib/marc/dump.rb` (`Marc::Dump`) | `test/lib/marc/dump_test.rb` |
| `sink` | `json_array` | `lib/json_array.rb` (`JsonArray`) | `test/lib/json_array_test.rb` |

`test/` mirrors the directories, as in Rails, so that a source and a job of
the same name do not share a test file.

- Jobs, transforms and commands take names as `Names.valid?` defines them.
  In file names, `-` becomes `_` (`es:create-index` →
  `commands/es/create_index.rb`), since Ruby file names are snake case
  (RuboCop `Naming/FileName`).
- Sources and sinks are classes, not declarations: their names are not part
  of the project's namespace. Each part must match `[a-z][a-z0-9_]*` (a
  letter first, no `-`), so that it maps to a Ruby constant: the parts are
  camel-cased at `_` (`json_array` → `JsonArray`, `marc2json` → `Marc2json`)
  and joined with `::`.
- A source or sink must not reopen a class that Ruby or metacrunch defines:
  the first constant must be undefined, or a module when more parts follow
  (`metacrunch:lines` → `Metacrunch::Lines`). `file` would reopen `File`
  and is refused.

### 3.2 Paths

A path works with or without a project and is taken as given, relative to
the working directory. `.rb` is appended if missing. The name is the file's
base name (`tools/fix.rb` → job `fix`), the class of a source or sink the
camel-cased base name (`lib/json_array.rb` → `JsonArray`), both checked by
the rules of 3.1. A name with parts needs the name form.

With `--test`, the test goes to `test/BASENAME_test.rb` relative to the
working directory, as today, and loads the file by its path (section 6.6).

### 3.3 Test default

A name creates a test, a path does not; `--test` and `--no-test` override
both.

### 3.4 Executable files

Jobs, transforms and commands start with `#!/usr/bin/env metacrunch` and get
mode `0755`, in both forms, so that they run as `./jobs/catalog/ids.rb` too.
Sources, sinks and tests get the default mode.

## 4. Checks of `generate`

### 4.1 Before writing

Each is a usage error (exit 2), and nothing is written:

| Case | Message |
|---|---|
| No kind | `no kind given (job, transform, command, source or sink)` |
| Unknown kind | `unknown kind x (job, transform, command, source or sink)` |
| No name or path | `no name or path given` |
| More arguments | `unexpected arguments: a b` |
| Path ends with `/` | `jobs/ is a directory; give a file name` |
| Invalid name | `"Catalog" is not a valid job name; use a-z, 0-9, _ and -, in parts separated by :` |
| Invalid file name (path) | `MyJob.rb: "MyJob" is not a valid job name; use a-z, 0-9, _ and -` (as today) |
| Invalid source or sink name | `"marc-dump" is not a valid source name; use a-z, 0-9 and _, starting with a letter, in parts separated by :` (path: `marc-dump.rb: …`, without the parts) |
| Source or sink that would reopen a class | `"file" would reopen File; choose another name` |
| Reserved name | `"run" is the name of a built-in command; choose another name` (path: `run.rb: … choose another file name`, as today) |
| Name without project | `no Metacrunchfile found in DIR or above; give a path (./ids.rb) or create a project with metacrunch new` |
| Name declared in another file | `catalog:ids is already declared in commands/catalog.rb` |
| `--desc` for a source or sink | `--desc is for jobs, transforms and commands` |
| `--desc` with a line break | `desc must be one line of text` |
| A file exists, no `--force` | `jobs/catalog/ids.rb, test/jobs/catalog/ids_test.rb already exist; use --force to overwrite` (`exists` for one file) |
| `Metacrunchfile` fails (name form) | its message, as for `run NAME` |

- A name declared in the target file itself is no conflict of names: with
  `--force`, `generate` overwrites that file like any other.
- Writing is all or nothing as far as the checks go: if one file exists,
  none is written. `--force` overwrites files, never names declared
  elsewhere.
- The name form loads the project through the CLI's `ProjectLookup`, so
  files that do not load give their usual warnings once.

### 4.2 After writing

For jobs, transforms and commands, if a project lies at or above the new
file's directory, `generate` loads that project again (a fresh
`Project.load_file`, not the cached lookup, without warnings) and looks at
the new name:

| Case | Line on stderr |
|---|---|
| The new file failed to load | `warning: ` + the project's load error summary of the file |
| The name is declared twice (only possible for a path) | `warning: ` + the project's duplicate message |
| The name is missing | `note: tools/fix.rb is not loaded by the Metacrunchfile; it runs by path only` |

The note is often intended for a path. For a name it means that the
`Metacrunchfile`'s globs are not recursive (`jobs/*.rb`). If the
`Metacrunchfile` itself fails (possible for a path only, since the name form
loaded it before), the check is skipped with `warning: ` + the first line of
its error. None of these changes the exit status: the files are written.

### 4.3 Output

One line per written file on stdout, with the path relative to the working
directory, also when `generate` runs in a subdirectory of the project:

```
created ../jobs/catalog/ids.rb
created ../test/jobs/catalog/ids_test.rb
```

Sources and sinks add how to use them (`sink Marc::Dump.new(...)` for a
sink):

```
created lib/marc/dump.rb
created test/lib/marc/dump_test.rb
In a job: require_relative the file, then source Marc::Dump.new(...)
```

## 5. `new`

### 5.1 Files

`metacrunch new catalog`:

```
catalog/
├── Metacrunchfile
├── Gemfile
├── Rakefile
├── jobs/.keep
├── transforms/.keep
├── commands/.keep
├── lib/.keep
└── test/
    ├── test_helper.rb
    └── project_test.rb
```

Every file starts with a short comment on what it is for. The contents,
without those comments:

```ruby
# Metacrunchfile
Metacrunch.load_files "jobs/**/*.rb", "transforms/**/*.rb", "commands/**/*.rb"
```

```ruby
# Gemfile
source "https://rubygems.org"

gem "metacrunch", "~> 5.0"

group :test do
  gem "minitest"
  gem "rake"
end
```

The `metacrunch` line follows `Metacrunch::VERSION`: a release gives
`"~> MAJOR.MINOR"`, a prerelease (`5.0.0.pre`) gives
`github: "ubpb/metacrunch", branch: "metacrunch-ng"`.

```ruby
# Rakefile
require "minitest/test_task"

Minitest::TestTask.create    # test/**/*_test.rb, with lib and test on the load path

task default: :test
```

```ruby
# test/test_helper.rb
$LOAD_PATH.unshift(File.expand_path("../lib", __dir__))

require "minitest/autorun"
require "metacrunch"
require "metacrunch/testing"

PROJECT = Metacrunch.load_project(File.expand_path("..", __dir__))
```

```ruby
# test/project_test.rb
require_relative "test_helper"

class ProjectTest < Minitest::Test

  def test_all_files_load_and_every_name_is_unique
    assert_empty PROJECT.load_errors
    assert_empty PROJECT.duplicates
  end

end
```

The test of the project catches every generated or edited file that does
not load. Tests of names require the helper with `require_relative`, so a
single test file also runs with plain `ruby test/jobs/catalog/ids_test.rb`.

### 5.2 Rules

| Case | Result |
|---|---|
| `DIR` does not exist | created, with parents |
| `DIR` is empty, or `.` in an empty directory | used |
| `DIR` holds some of the files of 5.1 | usage error listing them, unless `--force` |
| `DIR` holds other files only | used; other files are never changed or deleted |
| `DIR` is a file | usage error `catalog is a file` |
| `DIR` ends with `.rb` | usage error `new creates a project; for a job file use metacrunch generate job DIR` (DIR as given) |
| No `DIR` | usage error `no directory given` |
| More arguments | usage error `unexpected arguments: a b` |
| `DIR` lies inside another project | created, with `note: inside the project /path; below catalog/ names resolve in the new project` |

`new` runs no `git init` and no `bundle install`, and creates neither
`.gitignore` (nothing needs ignoring; `credentials edit` writes its own
`.metacrunch/.gitignore`) nor credentials.

### 5.3 Output

```
created catalog/Metacrunchfile
created catalog/Gemfile
…
Next steps:
  cd catalog
  bundle install
  bundle exec metacrunch generate job NAME
  bundle exec rake
```

The `cd` line names DIR as given, shell-escaped; for `new .` it is left out.

## 6. Templates

The templates below show the name form; section 6.6 lists what the path
form changes. Generic names only. They follow the repository's RuboCop
configuration (rubocop-ubpb `ruby.yml`), which the end-to-end test checks.

### 6.1 Job

```ruby
#!/usr/bin/env metacrunch
# frozen_string_literal: true

# Reads JSON Lines from stdin and writes them to stdout:
#   metacrunch catalog:ids < in.jsonl > out.jsonl
# Declare a source or a sink to read or write elsewhere.
Metacrunch.job "catalog:ids" do
  params do
    # param :input, String, required: true, desc: "JSON Lines file"
  end

  # source MySource.new(params.input), id: ->(record) { record["id"] }

  reject("No id") { it["id"].nil? }
  # use "catalog:clean", lang: "en"
  map do |record, ctx|
    ctx.mark("No title") unless record.key?("title")
    record
  end

  # sink MySink.new, batch: 1000
end
```

With `--desc "Extract the ids"` the declaration reads
`Metacrunch.job "catalog:ids", desc: "Extract the ids" do`.

```ruby
# test/jobs/catalog/ids_test.rb
# frozen_string_literal: true

require_relative "../../test_helper"

class CatalogIdsJobTest < Minitest::Test

  def test_keeps_records_with_an_id
    result = Metacrunch::Testing.run(PROJECT.fetch("catalog:ids"), source: [{"id" => 1}, {"title" => "x"}])

    assert_equal [{"id" => 1}], result.records
  end

end
```

The test class is the camel-cased name plus the kind (`CatalogIdsJobTest`,
`CatalogCleanTransformTest`, `CatalogReleaseCommandTest`), since jobs,
transforms and commands may share names with sources and sinks, whose test
classes have no kind (`MarcDumpTest`). A name that starts with a digit puts
the kind first, so that the class is a constant: `2go` → `Job2goTest`, as
today.

### 6.4 Source

```ruby
# frozen_string_literal: true

module Marc
  # A source: yields a record for each line of a file. The file is read in
  # each, not in new, so that --help, check and tests with another source
  # read nothing. In a job:
  #   source Marc::Dump.new(params.input)
  class Dump

    def initialize(path)
      @path = path
    end

    # Optional: called once before the first record, with context.params
    # and context.logger.
    # def open(context) = nil

    def each
      File.foreach(@path, chomp: true) { |line| yield({"line" => line}) }
    end

    # Optional: called at the end, also after an error.
    # def close = nil

  end
end
```

Each part but the last becomes a `module` around the class. The test writes
a file into a temporary directory and checks the records of
`Marc::Dump.new(path).enum_for(:each).to_a`.

### 6.5 Sink

```ruby
# frozen_string_literal: true

require "json"

module Marc
  # A sink: writes each record as a line of JSON into a file. In a job:
  #   sink Marc::Dump.new(params.output)
  class Dump

    def initialize(path)
      @path = path
    end

    # Called once before the first record.
    def open(_context)
      @file = File.open(@path, "w")
    end

    def write(record)
      @file.puts(JSON.generate(record))
    end

    # Optional: with `sink Marc::Dump.new(...), batch: 1000` the job calls
    # write_batch with up to 1000 records instead of write.
    # def write_batch(records) = records.each { write(it) }

    # Called at the end, also after an error.
    def close
      @file&.close
    end

  end
end
```

The test opens the sink with `nil` as context, writes two records, closes
it and compares the file.

### 6.6 Path form

| | Name form | Path form |
|---|---|---|
| Run line in the comment | `metacrunch catalog:ids < in.jsonl …` | `metacrunch run tools/fix.rb < in.jsonl …` (the path as given) |
| Test file | `test/<mirror>_test.rb` below the root | `test/BASENAME_test.rb` below the working directory |
| Test setup | `require_relative` of `test_helper`, `PROJECT.fetch(name)` | self-contained: `minitest/autorun`, `metacrunch`, `metacrunch/testing`, and the file by its path relative to the test |
| Job, transform, command | — | `Metacrunch.load_job(FILE)`, `load_transform(FILE)`, `load_command(FILE)` |
| Source, sink | `require "marc/dump"` (lib on the load path) | `require_relative` of the file |
| Modules of a source or sink | one per part but the last | none (the base name only) |

## 7. Ruby API and testing

```ruby
command = Metacrunch.load_command("tools/release.rb")       # name: selects one of several
run = Metacrunch::Testing.invoke(command, params: {}, stubs: {})
run = Metacrunch::Testing.invoke(command, stubs: {"catalog" => :ok}, project: PROJECT)
run = Metacrunch::Testing.invoke(PROJECT, "catalog:release")  # as before
```

- `Metacrunch.load_command(path, name: nil)` loads a command file like
  `load_job` and `load_transform` (`Loader.load(..., kind: Command)`), with
  the hint `select one with name:`.
- `Testing.invoke` takes a `Command` as its first argument, with an optional
  `project:` keyword, besides `(project, name)`. Any other first argument
  raises `ArgumentError`; so does a name next to a command, or `project:`
  next to a project.
- With `project:`, names of `invoke` and of stubs resolve in that project,
  as before. Without, they resolve in the nearest project of the working
  directory, loaded on first use, as `Testing.run` does for `use`; with no
  project there, a stub for a name raises `ArgumentError` and an `invoke`
  of a name `InvokeError`, as a real run outside a project does. Files work
  either way.

## 8. Architecture

The generators compute; the commands of the CLI parse, check, write and
print.

| Unit | Responsibility |
|---|---|
| `Generators::Target` | kind + name or path + working directory + project root → file, test file, name, class name, modules; validation of names (Data) |
| `Generators::Template` | renders an ERB file of `lib/metacrunch/templates/` with locals (`ERB.new(text, trim_mode: "-")`, `result_with_hash`) |
| `Generators::Plan` | files to write (`path => content`) and which are executable; conflicts, writing, `created` lines |
| `Generators::Files` | the file and the test of a job, transform, command, source or sink; wraps sources and sinks in their modules |
| `Generators::Skeleton` | the project skeleton; the Gemfile line from `VERSION` (not `Generators::Project`, which would hide `Metacrunch::Project` inside the module) |
| `Cli::NewCommand` (rewritten) | `new`: options, rules of 5.2, notes, next steps |
| `Cli::GenerateCommand` | `generate`: options, checks of 4.1, check of 4.2, output |

- Templates live in `lib/metacrunch/templates/{project,job,transform,command,source,sink}/`
  as `*.erb`, one file per template and form (for example `job/file.rb.erb`,
  `job/test.rb.erb`, `job/path_test.rb.erb`). The gemspec adds
  `lib/**/*.erb` to `files`.
- `Metacrunch.load_command` goes into `lib/metacrunch.rb`; `Testing.invoke`
  dispatches on its first argument.
- `Names::RESERVED` gains `generate`.
- The old `job_template`, `test_template` and `class_name` of
  `Cli::NewCommand` go away.

## 9. Exit codes

| Code | `new`, `generate` |
|---|---|
| 0 | files written (notes and warnings of 4.2 included) |
| 1 | an unexpected error while writing (for example a permission error) |
| 2 | a usage error of 4.1 or 5.2; nothing written |

## 10. Tests

### 10.3 End to end

In a temporary directory and without `bundle install`. Files are generated
in-process through `Metacrunch::Cli` (the command tests cover the CLI);
jobs, generated tests and RuboCop run in subprocesses, jobs through
`exe/metacrunch`:

- `new catalog`, then in `catalog/jobs/` (a subdirectory) `generate` of all
  five kinds by name. `metacrunch --help` lists the job, transform and
  command; each of them runs on JSON Lines from stdin (the command without
  input); the generated tests pass with
  `ruby -I LIB -e 'ARGV.each { require File.expand_path(it) }' test/**/*_test.rb`.
- The five kinds by path with `--test`, outside any project: each file runs
  by path, the tests pass.
- RuboCop with the repository's `.rubocop.yml`, in one run over both trees,
  reports no offense for the files it selects by default: every `.rb`, the
  `Gemfile` and the `Rakefile`. The `Metacrunchfile` is not among them, as
  in a project's own RuboCop run; `Prism.parse` checks it (10.1).
