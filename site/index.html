Metadata pipelines in plain Ruby

metacrunch is a small toolkit for data processing and ETL. A job reads records from a source, passes them through steps and writes them to a sink. Rejected and failed records keep their reason, and jobs chain with each other and with jq, grep and sort.

Get started See how it works 
gem "metacrunch", github: "ubpb/metacrunch"

Until the release of metacrunch 5, the gems come from Git with Bundler. Requires Ruby 4.0.

How it works

A job is a Ruby file

Sources, steps and sinks are plain Ruby objects. A source is anything with #each, a sink anything with #write. metacrunch run runs the job and prints a summary.

numbers.rb
Metacrunch.job "numbers" do
  params do
    param :factor, Integer, default: 2, desc: "Multiplier"
    args :numbers, min: 1, desc: "Numbers to process"
  end

  source params.numbers.map { Integer(it) }

  reject("Negative") { it.negative? }
  map { it * params.factor }
end
shell
$ metacrunch run numbers.rb --factor 3 -- 1 2 -5
3
6
INFO  ok: read 3, written 2, rejected 1 (Negative: 1) in 0.00s

$ metacrunch run numbers.rb --help
# lists --factor and the arguments
map1 record → 1

The block returns the new record.

filter1 record → 0 or 1

Keeps the record when the block is truthy.

reject1 record → 0 or 1

Drops the record when the block is truthy. With a reason, it is counted and sent to rejects.

flat_map1 record → 0 to n

The block returns an Enumerable of records.

Jobs

A source, steps and a sink. Without a source a job reads JSON Lines from stdin, without a sink it writes them to stdout.

Metacrunch.job "marc_to_json" do … end

Transforms

Named steps with parameters of their own, which several jobs share with use.

use "normalize", params: {max_length: 40}

Commands

Ruby code that runs jobs, transforms and other commands with invoke and acts on their results: for example, it publishes the new data only when the job ran without errors.

result = invoke "marc_to_json"
publish if result.ok?   # your code

metacrunch is developed at Paderborn University Library and grew out of its metadata work. Nothing in it is specific to library data, though: a record is any Ruby object, usually a Hash.

Features

What comes with every job

Trace a job

metacrunch trace runs the first records, or the records at a position or with an id, and shows what every step did: the changed keys of a Hash, marks, rejections and failures. It changes nothing: all sinks are replaced, and hooks do not run.

The engine counts records per step and per reason, so the summary of a run says why records went missing.

The example traces the job books:export: it writes the public titles into a directory, with the steps of the transform books:public.

shell
$ metacrunch trace -n 1 books:export --output out
#1  id=t1
  books:public/reject#1  pass
  books:public/map#2     - "public": true
  sink                   1 record (not written)
traced 1 record: 1 to sink

$ metacrunch trace --position 3 books:export --output out
#3  id=t3
  books:public/reject#1  rejected: Not public
traced 1 record: 0 to sink, 1 rejected

Unix pipes

Jobs read and write JSON Lines on stdin and stdout, and every stage runs in its own process. Logs and the summary go to stderr.

shell
$ metacrunch run hello.rb \
    | jq -c 'select(.name != "Grace")' \
    | metacrunch run normalize.rb
{"name":"Ada","greeting":"Hello, Ada!"}
{"name":"Linus","greeting":"Hello, Linus!"}

Workers, in source order

-w N runs the steps in N processes. Records reach the sinks in source order, so a job gives the same results with and without workers. With about 28 µs of work per record, 8 workers were about 5× as fast; cheap steps run faster inline.

shell
$ metacrunch run -w 8 books:export --output out
$ metacrunch run -w auto books:export --output out
# auto: one worker per core but one

Rejects and failures

Rejected and failed records go to sinks of their own, with their context. A failure policy per job decides whether a failing record stops the run or is skipped; the exit status tells the two apart.

job
reject("Not public") { !it["public"] }

rejects  Metacrunch::JsonLines::ContextWriter.new("rejects.jsonl")
failures Metacrunch::JsonLines::ContextWriter.new("failures.jsonl")
on_failure :skip   # exit status 3 when records failed

Parameters, secrets, environments

A value comes from the command line, else from the environment's section of a params file, else from the default. {env: …} reads a variable, {credential: …} the encrypted credentials. A secret stays out of help, messages and logs.

params
params do
  param  :limit, Integer, default: 1000
  param  :es_url, String, default: {env: "ES_URL"}
  secret :api_key, String, default: {credential: "es.api_key"}
  args   :files, min: 1
end

Tests with Minitest

Metacrunch::Testing.run replaces the source by the records you give and the sinks by memory, so nothing is written. Testing.invoke runs a command and records what it invokes.

test/jobs/books/export_test.rb
records = [{"id" => "t1", "title" => "A", "public" => true},
           {"id" => "t2", "title" => "B", "public" => false}]
result = Metacrunch::Testing.run(PROJECT, "books:export",
                                 params: {output: "unused"},
                                 source: records)

assert_equal [{"id" => "t1", "title" => "A"}], result.records

Projects and generators

A Metacrunchfile gives jobs, transforms and commands names, which run from any directory of the project. generate writes a job, transform, command, source or sink that runs right away, with a test that passes.

shell
$ metacrunch new book-data
$ metacrunch generate job books:clean
$ metacrunch check books:clean
# builds the job and binds its parameters, runs nothing

metacrunch-marc

MARC in three syntaxes, on one record model

The reader tells the format of each file by its content, so the same job reads binary MARC (ISO 2709, .mrc), MARCXML and MARC-in-JSON, also gzip-compressed. Parsers keep the data as written and check that values are valid UTF-8 that XML 1.0 can represent.

jobs/marc2jsonl.rb
require "metacrunch/marc"

Metacrunch.job do
  params { args :files, min: 1 }

  source Metacrunch::Marc::Reader.new(params.files),
         id: ->(record) { record["001"]&.value }

  map do |record|
    {
      "id" => record["001"]&.value,
      "title" => record.field("245")&.join("a", "b", separator: " : "),
      "authors" => record.values(["100", "700"], "a"),
      "isbns" => record.values("020", "a")
    }
  end
end
shell
$ metacrunch run jobs/marc2jsonl.rb records.mrc more-records.xml.gz \
    > records.jsonl

Query, change, write

Queries take tags, ranges and patterns, with indicator filters: record.fields("600".."699"), record.values("650", "a", ind2: "7"). Results are plain Arrays.

record.to_s shows one line per field, as on the card at the top of this page, so records stay readable in trace and in test failures.

  • Reads and writes ISO 2709 (binary MARC, .mrc), MARCXML and MARC-in-JSON.
  • Changes go through add, append, remove and clear, which keep the field index right.
  • One dependency besides metacrunch: Ox, for MARCXML.

Where metacrunch fits

Other tools cover the same ground, each with its own approach. If you know one of them, this is what is different.

Catmandu

Perl

A toolkit for library data with the Fix language and a large set of importers, exporters and stores.

metacrunch has no mapping language of its own. Steps are Ruby blocks, so the whole of Ruby and its gems is at hand.

Metafacture

Java

A toolkit for semi-structured data with a focus on library metadata, with workflows in Flux and transformations in Fix or the older Metamorph.

In metacrunch, jobs, their parameters and their tests are all Ruby.

Traject

Ruby

A transformation system for library, archive and museum metadata, MARC and XML, configured with to_field rules and indexing to Solr above all.

metacrunch is general ETL: any source, any sink. MARC is one extension gem among others.

Kiba

Ruby

A lightweight ETL framework for Ruby: sources and destinations are classes, transforms classes or blocks. Its author considers it done and keeps it compatible with new Ruby versions.

metacrunch comes with a command line, projects, parameters and credentials, reject reasons, tracing and workers.

Pick metacrunch when you want to write jobs in Ruby, test them with Minitest and run them like Unix tools.

Get started

From an empty directory to a tested job

metacrunch 5 is not released yet, so the gems come from Git. The commands below call metacrunch; with Bundler, prefix them with bundle exec.

  1. Add the gems

    Name the gems you need. All of them require Ruby 4.0.

    Gemfile
    git "https://github.com/ubpb/metacrunch.git" do
  gem "metacrunch"
  gem "metacrunch-marc"
end

  2. Install and look around

    shell
    $ bundle install
$ bundle exec metacrunch --help

  3. Create a project

    new creates the project with a Metacrunchfile, a Gemfile, a Rakefile and a test that every file loads.

    shell
    $ metacrunch new book-data
$ cd book-data
$ bundle install

  4. Generate, run and test a job

    The generated job reads JSON Lines from stdin and rejects records without an id. Its test passes from the start.

    shell
    $ metacrunch generate job books:clean
$ printf '{"id":1,"title":"A"}\n{"title":"B"}\n' | metacrunch run books:clean
{"id":1,"title":"A"}
INFO  ok: read 2, written 1, rejected 1 (No id: 1) in 0.00s
$ rake test
